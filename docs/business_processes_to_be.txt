SUSPENSEMANAGER — ОПИСАНИЕ БИЗНЕС-ПРОЦЕССОВ (TO-BE)
Автоматизированная система обработки невалидных стриминговых записей


1. НАЗНАЧЕНИЕ СИСТЕМЫ И КЛЮЧЕВЫЕ ПОНЯТИЯ

SuspenseManager автоматизирует обработку невалидных записей из отчётов стриминговых платформ (Yandex Music, Apple Music, Spotify, YouTube Music). Каждая запись в отчёте описывает факт стриминга: какой музыкальный продукт воспроизводился, на какой территории, по какому договору, в каком количестве и на какую сумму.

Запись называется суспенсом, если автоматическая проверка выявила одну из двух проблем. Первая — нет продукта: музыкальный продукт (трек или альбом), упомянутый в отчёте, не найден в каталоге компании. Без идентифицированного продукта невозможно определить правообладателя и начислить роялти. Вторая — нет прав: продукт в каталоге найден, но для него не определены права — не указано, кто из компаний-правообладателей и в какой доле должен получить вознаграждение по данному договору и территории.

Записи, успешно прошедшие обе проверки, получают статус «Валидировано» и немедленно уходят в расчёт роялти, не задерживаясь в системе.

Суспенсы обрабатываются не по одному, а пакетами — группами. Оператор объединяет похожие суспенсы в группу и решает проблему сразу для всего пакета.


2. СТАТУСНАЯ МОДЕЛЬ

Каждая запись суспенса и каждая группа имеют статус обработки. Статус определяет, на каком этапе находится объект и какие действия с ним доступны.

Статус «Нет продукта» (0) означает, что запись не входит в группу и продукт не найден. Статус «Нет прав» (1) — запись не в группе, продукт найден, права не определены. Статус «В группе, нет продукта» (15) — запись входит в активную группу, продукт не установлен. Статус «В группе, нет прав» (16) — запись в активной группе, продукт установлен, прав нет. Статус «Отложено, нет продукта» (30) — группа отложена, ветка без продукта. Статус «Отложено, нет прав» (32) — группа отложена, ветка без прав. Статус «Валидировано» (88) — запись успешно обработана и передана в расчёт роялти. Статус «Бэк-офис, нет продукта» (120) — группа передана специалисту бэк-офиса, продукт не установлен. Статус «Бэк-офис, нет прав» (320) — группа у специалиста бэк-офиса, права не определены.

Принципиальное правило: записи ветки «нет продукта» и записи ветки «нет прав» никогда не смешиваются в одной группе. Все записи группы обязаны принадлежать одной ветке обработки. Статус каждой записи всегда совпадает со статусом её группы — при любом изменении статуса группы система автоматически обновляет статус всех входящих в неё записей.


3. БИЗНЕС-ПРОЦЕСС 1. ЗАГРУЗКА И АВТОМАТИЧЕСКАЯ ВАЛИДАЦИЯ ОТЧЁТОВ

Цель: принять отчёт стриминговой платформы, автоматически проверить каждую строку и сохранить результат с корректным статусом.

3.1. Разбор файла и форматная проверка

Система читает загруженный Excel-файл. Заголовки колонок могут различаться у разных платформ — система сопоставляет их автоматически по ключевым словам. До сохранения каждая строка проходит форматную проверку: наличие обязательных полей (ISRC или штрихкод, название трека, исполнитель), корректность числовых значений (количество воспроизведений больше нуля, цена, курс обмена).

Если хотя бы одна строка не проходит проверку, вся загрузка прерывается. Оператору возвращается список строк с конкретными ошибками и номерами строк в Excel.

3.2. Автоматический поиск продукта в каталоге

Для каждой строки система ищет соответствующий продукт в каталоге компании по приоритетной цепочке. Каждый следующий критерий применяется только в том случае, если предыдущий не дал результата.

Первый приоритет — поиск по ISRC (точное совпадение). Второй — поиск по штрихкоду (точное совпадение). Третий — одновременное совпадение названия трека и исполнителя. Четвёртый — совпадение каталожного номера. Поиск ведётся только среди активных, не удалённых продуктов.

Если продукт найден, строка связывается с ним. Если ни один критерий не дал результата, строка получает статус «Нет продукта» (0).

3.3. Автоматический поиск прав на продукт

Поиск прав выполняется только для строк, по которым продукт был найден. Система ищет запись о правах по полному совпадению всех условий одновременно: найденный продукт, номер договора из строки отчёта, код территории из строки отчёта, компания-отправитель и компания-получатель.

Если номер договора, код территории или сведения о компаниях отсутствуют, строка сразу получает статус «Нет прав» (1). Поиск ведётся только среди полностью заполненных записей о правах, пригодных для расчёта роялти.

3.4. Присвоение статуса и сохранение результата

По итогам проверок каждой строке присваивается один из трёх статусов. Статус 0 — продукт не найден ни по одному критерию. Статус 1 — продукт найден, но права не определены. Статус 88 — продукт найден и права определены; такая запись немедленно передаётся в расчёт роялти.

Оригинальные данные из отчёта платформы сохраняются в неизменном виде на всём протяжении работы системы — это обеспечивает юридическую корректность исходного материала. Каждая созданная запись фиксируется в журнале аудита с начальным статусом.

Оператору возвращается сводка: общее количество строк в файле, количество валидированных, количество без продукта, количество без прав, а также детальный результат по каждой строке с указанием причины суспенса.


4. БИЗНЕС-ПРОЦЕСС 2. ГРУППИРОВКА ЗАПИСЕЙ СУСПЕНСОВ

Цель: объединить похожие записи суспенсов в группу для пакетной обработки. Групповая обработка кратно сокращает количество рутинных операций при большом объёме невалидных записей.

Обязательное ограничение: записи ветки «нет продукта» и записи ветки «нет прав» не могут быть объединены в одну группу.

4.1. Предпросмотр групп

Оператор задаёт параметры группировки: ветка обработки (нет продукта или нет прав), набор признаков для объединения, фильтры, порядок сортировки и размер страницы.

Для ветки «нет продукта» объединение может вестись по следующим признакам: ISRC, штрихкод, каталожный номер, исполнитель, название трека, жанр, компания-отправитель, компания-получатель, оператор, тип договора, номер договора, территория.

Для ветки «нет прав» объединение ведётся по признакам продукта из каталога (ISRC, штрихкод, каталожный номер, название, исполнитель) и по реквизитам из строки отчёта (компания-отправитель, компания-получатель, оператор, тип договора, номер договора, территория). Идентификатор продукта всегда является обязательным признаком группировки в этой ветке.

Система агрегирует записи по выбранным признакам и возвращает постраничный список потенциальных групп. Для каждой группы отображается количество записей и суммарная выручка (количество воспроизведений, умноженное на цену и курс обмена). Поддерживается фильтрация по диапазонам количества записей и выручки.

4.2. Фиксация группы

Оператор выбирает строку из предпросмотра и подтверждает создание группы. Система находит все записи суспенсов, соответствующие выбранным значениям признаков, и выполняет следующие действия в рамках одной неделимой операции.

Создаётся группа с соответствующим статусом: для ветки «нет продукта» — статус 15, для ветки «нет прав» — статус 16. Автоматически формируются начальные сведения о продукте для группы на основе значений выбранных признаков — если оператор группировал по исполнителю и названию, эти значения сразу сохраняются как описание продукта группы.

Все найденные записи суспенсов прикрепляются к созданной группе и получают её статус. Для каждой записи сохраняется историческая отметка о членстве в группе — она остаётся даже после возможной разгруппировки и служит для аудита. Все изменения фиксируются в журнале. При любой ошибке вся операция отменяется целиком.


5. БИЗНЕС-ПРОЦЕСС 3. ОБРАБОТКА ГРУППЫ БЕЗ ПРОДУКТА (СТАТУС 15)

Цель: установить, какой продукт из каталога соответствует записям группы, и либо создать новый продукт, либо привязать существующий.

5.1. Просмотр группы и уточнение сведений о продукте

При открытии группы оператор видит список записей суспенсов. Если оператор заполнил уточняющие сведения о продукте для группы (например, скорректировал название или исполнителя), система отображает эти уточнённые данные вместо оригинальных из отчёта. Оригинальные данные при этом остаются неизменными в системе.

Оператор может в любой момент обновить описание продукта для группы: название, исполнитель, ISRC, штрихкод, каталожный номер, жанр, тип формата, дата релиза. После того как группа привязана к продукту из каталога, эти поля блокируются — сведения о продукте отображаются напрямую из каталога.

5.2. Быстрая каталогизация (переход 15 → 16)

Действие позволяет создать новый продукт в каталоге компании непосредственно из описания, заполненного оператором для группы. Предусловие: должны быть заполнены все обязательные идентификационные поля — название, исполнитель, ISRC, штрихкод, каталожный номер. Если что-то отсутствует, система сообщает, каких именно данных не хватает.

При выполнении операция проверяет уникальность продукта в каталоге, чтобы не создать дубль. Затем новый продукт добавляется в каталог, и группа привязывается к нему. Статус группы меняется с 15 на 16 — всегда именно на 16, а не сразу на 88, поскольку у только что созданного продукта не может быть прав по определению. Группа переходит в ветку «нет прав» для дальнейшей обработки.

5.3. Поиск похожих продуктов в каталоге

Если оператор предполагает, что нужный продукт уже есть в каталоге, система выполняет поиск кандидатов. Поиск ведётся по нескольким критериям одновременно: точное совпадение ISRC, точное совпадение штрихкода, вхождение названия в наименование продукта, вхождение имени исполнителя. Данные для поиска берутся из уточняющих сведений, заполненных оператором, а при их отсутствии — из первой записи группы. Результат — постраничный список продуктов-кандидатов из каталога.

5.4. Привязка существующего продукта (переход 15 → 16 или 15 → 88)

Оператор выбирает продукт из каталога и привязывает его к группе. Система проверяет, что карточка выбранного продукта заполнена полностью: обязательно наличие названия, исполнителя, ISRC, штрихкода и каталожного номера. Если продукт неполный, операция блокируется с рекомендацией обратиться к специалистам каталога или отправить группу в бэк-офис.

Если продукт прошёл проверку, описание продукта для группы синхронизируется с данными из каталога, и продукт привязывается к группе. Затем система проверяет, определены ли права для этого продукта. Если полные права уже есть — группа сразу получает статус «Валидировано» (88) и обработка завершается. Если прав нет — статус меняется на 16 и группа переходит в ветку «нет прав».

5.5. Откладывание (переход 15 → 30)

Если группу невозможно обработать в текущий момент, оператор откладывает её с указанием причины. Статус меняется с 15 на 30. Группа переходит в раздел отложенных.

5.6. Отправка в бэк-офис (переход 15 → 120)

Если случай сложный и требует участия специалиста, оператор отправляет группу в бэк-офис с текстовым описанием проблемы. Система проверяет, что для данной группы нет уже открытого задания, создаёт задание для специалиста и меняет статус с 15 на 120.

5.7. Разгруппировка (переход 15 → 0)

Оператор может расформировать группу. Группа удаляется из активной обработки, а все входившие в неё записи суспенсов возвращаются в статус «Нет продукта» (0) и снова становятся доступны для новой группировки. История о том, что запись входила в группу, сохраняется для аудита. Если к записям уже была установлена связь с продуктом каталога, эта связь сохраняется — информация не теряется.


6. БИЗНЕС-ПРОЦЕСС 4. ОБРАБОТКА ГРУППЫ БЕЗ ПРАВ (СТАТУС 16)

Цель: определить права на установленный продукт и зафиксировать их, чтобы записи можно было передать в расчёт роялти.

Ключевое отличие от ветки без продукта: для групп статуса 16 сведения о продукте отображаются из каталога компании, а не из оригинальных строк отчёта. Продукт уже идентифицирован, его данные берутся из авторитетного источника.

6.1. Заполнение сведений о правах для группы

Оператор заполняет шаблон прав, который будет использован для создания официальной записи о правах в каталоге. Указываются компания-отправитель и компания-получатель (из справочника компаний), территория действия прав (из справочника территорий), реквизиты договора (номер, тип, дата), период действия (дата начала и окончания), доля вознаграждения в процентах.

При сохранении система проверяет корректность введённых данных: компания-отправитель и компания-получатель не могут совпадать; дата окончания должна быть позже даты начала; дата договора не должна быть позже даты начала действия; доля должна быть от 1 до 100 процентов.

6.2. Поиск прав в каталоге

Если аналогичные права уже определены для другого продукта в каталоге, их можно найти и скопировать. Система выполняет поиск по полям продукта (исполнитель, ISRC, название, штрихкод) с возможностью выбора логики объединения условий. Дополнительно можно фильтровать по территории и номеру договора. Результат — список найденных записей о правах с указанием продукта, к которому они относятся.

6.3. Копирование прав из каталога (переход 16 → 88)

Оператор выбирает подходящую запись о правах и копирует её к продукту текущей группы. Система проверяет отсутствие дублей: если идентичная комбинация договора, территории и компании-отправителя уже есть у продукта, повторная запись не создаётся, но операция успешно завершается. После этого группа получает статус «Валидировано» (88) и обработка завершается.

6.4. Создание прав из заполненного шаблона (переход 16 → 88)

Если нужных прав нет в каталоге, оператор создаёт их напрямую из шаблона прав, заполненного для группы. Предусловие: все обязательные поля шаблона должны быть заполнены. Если что-то отсутствует, система сообщает, каких данных не хватает. При успешной проверке создаётся официальная запись о правах в каталоге компании, и группа получает статус «Валидировано» (88).

6.5. Откладывание, отправка в бэк-офис, разгруппировка

Логика аналогична ветке без продукта с учётом соответствующих статусов. Откладывание переводит группу в статус 32. Отправка в бэк-офис — в статус 320 с созданием задания для специалиста. При разгруппировке записи возвращаются в статус «Нет прав» (1), при этом установленная ранее связь с продуктом каталога сохраняется.


7. БИЗНЕС-ПРОЦЕСС 5. ОТЛОЖЕННЫЕ ГРУППЫ (СТАТУСЫ 30, 32)

Цель: временно исключить группу из активной обработки с возможностью вернуться к ней позже.

Отложенные группы выделены в отдельный раздел системы. Для каждой группы сохраняется причина откладывания. Оператор может в любой момент вернуть группу в активную обработку: статус 30 меняется на 15, статус 32 — на 16. Причина откладывания при возврате очищается. Статусы всех записей обновляются автоматически, и группа снова становится доступна для всех действий своей ветки.


8. БИЗНЕС-ПРОЦЕСС 6. ОБРАБОТКА ЗАДАНИЙ В БЭК-ОФИСЕ (СТАТУСЫ 120, 320)

Цель: обработать сложные случаи, которые не смог разрешить оператор. Специалист бэк-офиса имеет расширенные полномочия и доступ к дополнительным инструментам работы с каталогом.

8.1. Просмотр задания

Специалист открывает задание и видит карточку группы с описанием продукта, список записей суспенсов, сведения о связанном продукте каталога, описание проблемы, переданное оператором, тип задания (нет продукта или нет прав), количество суспенсов в группе и информацию о наличии прав на продукт.

8.2. Уточнение сведений о продукте и правах

Специалист может уточнять описание продукта для группы и шаблон прав так же, как это делает оператор. Исключение: привязка продукта к группе выполняется только через специальное действие «Привязать продукт» — прямое указание продукта в описании для групп, находящихся в бэк-офисе, недоступно. Это необходимо для корректного прохождения жизненного цикла задания.

8.3. Привязка продукта (только для задания типа 120, переход 120 → 320 или 120 → 88)

Специалист выполняет поиск продукта-кандидата (нечёткий поиск по ISRC, штрихкоду, названию и исполнителю) и привязывает его к группе. Система проверяет наличие прав у выбранного продукта. Если права есть — группа сразу получает статус «Валидировано» (88) и задание закрывается. Если прав нет — группа переходит в статус 320 и специалист продолжает работу в ветке «нет прав». Описание продукта группы автоматически обновляется данными из каталога.

8.4. Поиск и применение прав (только для задания типа 320)

Специалист выполняет поиск подходящих прав в каталоге и копирует их к продукту группы — механизм аналогичен описанному в БП-4. Дополнительно доступна проверка текущих прав продукта: система показывает список всех записей о правах с указанием того, полностью ли они заполнены и пригодны ли для расчёта роялти.

8.5. Завершение задания (переход 320 → 88)

Когда специалист убеждён, что права установлены, он запускает финальную проверку и закрытие задания. Система проверяет наличие продукта у группы, затем ищет полностью заполненные права в каталоге. Если они найдены — группа получает статус «Валидировано» (88) и задание закрывается. Если нет — система пытается создать права из шаблона, заполненного специалистом. При наличии всех необходимых данных запись о правах создаётся в каталоге и группа переводится в статус 88. Если данных недостаточно — выводится сообщение с перечнем отсутствующих полей.

8.6. Возврат задания оператору

Если специалист считает, что оператор может справиться самостоятельно, он возвращает группу в активную обработку: статус 120 меняется на 15, статус 320 — на 16. Задание закрывается с пометкой «Возвращено оператору».

8.7. Удаление группы

Если группа не поддаётся обработке (например, данные в исходном отчёте изначально некорректны), специалист может удалить её. Все связанные данные — задание, группа, сведения о продукте и правах, записи суспенсов — помечаются как удалённые. Физически данные из системы не убираются: вся история остаётся доступной для аудита.


9. КЛЮЧЕВЫЕ АВТОМАТИЧЕСКИЕ МЕХАНИЗМЫ СИСТЕМЫ

9.1. Данные не удаляются физически

В системе не предусмотрено физического удаления записей. Любое удаление — это пометка об архивировании. Все запросы автоматически работают только с активными, не архивированными данными. Это гарантирует сохранность истории.

9.2. Журнал аудита

Каждое изменение статуса группы или записи суспенса автоматически фиксируется в журнале аудита: что изменилось, с какого статуса на какой. При первичной валидации каждая запись также логируется. Журнал позволяет в любой момент восстановить полную историю жизни любой записи или группы.

9.3. Синхронизация статусов

При любом изменении статуса группы система автоматически обновляет статус всех входящих в неё записей суспенсов. Нет риска рассогласованности между статусом группы и статусами её записей.

9.4. Атомарность составных операций

Все действия, затрагивающие несколько объектов одновременно (создание группы, смена статуса с созданием задания, разгруппировка, удаление), выполняются как единая неделимая операция. Если в ходе выполнения возникает ошибка, система полностью откатывает все изменения. Частичных или незавершённых состояний не возникает.

9.5. Расчёт выручки

Выручка по каждой записи суспенса вычисляется как произведение количества воспроизведений, цены и курса обмена. Этот показатель используется при предпросмотре группировки, в списках групп и при фильтрации. Значение вычисляется в момент запроса и не хранится отдельно.

9.6. Защита от дублирования прав

При копировании прав из каталога система проверяет, не существует ли уже идентичной записи у данного продукта (по договору, территории и компании-отправителю). Если такая запись уже есть, новая не создаётся, однако операция считается успешной.

9.7. История членства в группах

Каждая запись суспенса хранит два вида сведений о принадлежности к группе. Первый — текущая активная группа, которая очищается при разгруппировке. Второй — полная история всех групп, в которых когда-либо состояла запись; она сохраняется навсегда и не удаляется. Это позволяет ответить на вопрос, в каких группах когда-либо обрабатывалась та или иная запись.

9.8. Сохранение связи с продуктом при разгруппировке

При разгруппировке записей ветки «нет прав» установленная ранее связь с продуктом каталога сохраняется. Оператор не теряет уже выполненную работу по идентификации продукта — при повторной группировке эти записи уже будут содержать информацию о продукте.

9.9. Уточняющие сведения не затрагивают оригинал

Описание продукта и шаблон прав, которые оператор заполняет на уровне группы, никогда не перезаписывают оригинальные данные строк из отчёта платформы. Они отображаются поверх при просмотре, но исходные данные остаются нетронутыми. Это принципиально с юридической точки зрения: исходный отчёт платформы должен оставаться неизменным.
